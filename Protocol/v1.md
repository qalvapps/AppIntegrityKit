# AppIntegrity Protocol v1

## Rules

- HTTPS only outside local tests.
- JSON field names and enum values are case-sensitive.
- Binary values use unpadded RFC 4648 base64url.
- `keyID` is the opaque, padded standard-Base64 string returned by Apple and is
  not re-encoded as base64url.
- `protocolVersion` is the integer `1`.
- Challenges contain at least 32 random bytes, expire quickly, are purpose-bound,
  stored as hashes, and consumed exactly once.
- The server owns the security configuration behind `applicationID`.
- Error bodies never echo security artifacts.

## Endpoints

### `POST /v1/integrity/challenges`

Request:

```json
{"applicationID":"goodtides-ios","purpose":"attestation"}
```

Response:

```json
{
  "protocolVersion": 1,
  "challengeID": "opaque-server-id",
  "challenge": "unpadded-base64url-random-bytes",
  "purpose": "attestation",
  "expiresAt": "2026-07-14T16:00:00Z"
}
```

The same endpoint returns a new challenge with purpose `session` before an
assertion. A challenge for one purpose cannot satisfy the other.

### `POST /v1/integrity/attestations`

The client passes `SHA256(base64url_decode(challenge))` to Apple’s `attestKey`.
The server independently computes the same digest and gives those exact bytes
to the attestation verifier. It submits:

```json
{
  "protocolVersion": 1,
  "applicationID": "goodtides-ios",
  "challengeID": "opaque-server-id",
  "keyID": "apple-key-id",
  "attestationObject": "unpadded-base64url-cbor"
}
```

The server atomically consumes the challenge, performs every Apple validation
step against server-owned app configuration, verifies the key is not associated
with a conflicting subject, and stores the public key, receipt, environment,
optional signed validation metadata, and counter zero. The receipt is stored as
an opaque value for a separate Apple fraud-assessment flow.

Response:

```json
{"protocolVersion":1,"registered":true}
```

### `POST /v1/integrity/sessions`

The client constructs canonical session client data, hashes those exact bytes,
and passes the hash to Apple’s `generateAssertion`. It submits:

```json
{
  "protocolVersion": 1,
  "applicationID": "goodtides-ios",
  "keyID": "apple-key-id",
  "clientData": "unpadded-base64url-canonical-json",
  "assertion": "unpadded-base64url-cbor",
  "entitlementEvidence": "optional-unpadded-base64url"
}
```

The canonical JSON object has these fields:

```json
{
  "applicationID": "goodtides-ios",
  "challenge": "unpadded-base64url-random-bytes",
  "challengeID": "opaque-server-id",
  "entitlementEvidenceSHA256": "optional-unpadded-base64url-sha256",
  "keyID": "apple-key-id",
  "protocolVersion": 1,
  "requestedScopes": ["sorted", "unique"]
}
```

Encoding is UTF-8 JSON with lexicographically sorted object keys, no whitespace,
no escaped slashes, sorted unique scopes, and omitted optional values. The
server verifies the assertion over the exact decoded `clientData` bytes before
parsing them, then checks all fields and the entitlement-evidence hash.

Response:

```json
{
  "protocolVersion": 1,
  "sessionToken": "random-opaque-token",
  "expiresAt": "2026-07-14T16:30:00Z",
  "scopes": ["tides:forecast"]
}
```

The product backend stores only a hash of the opaque token. Requested scopes are
requests, not authority; the server returns only scopes allowed by verified
entitlement and product policy.

The verifier also checks signed assertion authenticator-data extensions against
server-owned policy when present. Apple assertions have been observed with both the
current `validationCategory` / `bundleVersion` names and the prefixed
`apple_validation_category_01` / `apple_bundle_version_01` names used by a
physical development device. The verifier accepts exactly one complete pair
and rejects partial, mixed, or duplicate pairs. Assertion counter comparison
and persistence must be one atomic transaction.

Pre-iOS 27 App Attest objects use the legacy grammar with no category/build
extension map. A backend may enable this grammar explicitly per application,
but only the exact legacy boundary is valid; non-empty trailing bytes must form
one complete supported extension map. Products enabling legacy compatibility
must compensate for the unavailable metadata with independently verified,
server-required authorization evidence. GoodTides uses Apple-signed StoreKit
evidence bound into the assertion's exact client data.

For Apple assertion signatures, first form
`nonce = SHA256(authenticatorData || SHA256(exactClientData))`, then verify the
ECDSA-with-SHA256 signature over the nonce bytes. The nonce is the message input
to ECDSA/SHA256, not a prehashed digest supplied through a prehashed API.

## Compatibility

Adding optional response fields is backward-compatible. Changing signed client
data, field meaning, binary encoding, challenge semantics, or verifier rules
requires a protocol compatibility decision and cross-language vectors. A client
must reject an unsupported `protocolVersion`.

The optional [Delegated Submission Grants v1](delegated-submission-grants-v1.md)
contract is additive. It does not change this protocol's challenges,
attestations, signed session client data, session response, or verifier rules.
